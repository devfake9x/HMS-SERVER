# Brainstorm: open the monitoring read actions (2026-11-06)

Modes: default (no --html / --wiki). Follows plan `261106-0735-do-relay-control` (done).

## Problem

13 of 94 catalog actions are open (11 reads + DO set_output/pulse). The device page shows only heartbeat
telemetry and DO state; operators cannot see sensor values (ADC, Modbus RTU tags), power, network or device
time without reading raw JSON in the C2 dialog. Reads are the cheapest, lowest-risk way to make the product
useful for monitoring.

## Facts found (scout)

- Opening a read = adding it to `EnabledActions` in `PinnedCommandCatalog.cs`; signing, reply verification,
  audit and per-device permission already work for every read.
- Catalog is pinned to HMS-IDF `83e93d77e` and generated by `scripts/generate-command-catalog.mjs` (reads §11
  via `git show`). Spec HEAD `18a63e8ed` (2026-11-05) adds 10 rows: `tags.list/get`,
  `modbus.get_rtu_devices/tags/live/diagnostics`, `sms.get`, `sms.send_status`, `sms.send` (B, confirm
  `SMS-SEND-<DEVID>`), `sms.delete` (D). New firmware permissions: `tag.view`, `mb_rtu.slave_view`,
  `mb_rtu.tag_view`, `mb_rtu.config_view`, `sms.send`, `sms.delete`. HMS-IDF working tree has uncommitted edits
  to `mqtt-api.md`; pin the commit, not the working copy.
- The real gateway (`hms_toan_lab/gateway_870c`, firmware 1.0.108) advertises 105 actions, including every
  action below.
- Spec maturity: only 9 reads are `SLICE_PASS` (all open). `modbus.get_rtu_status/config`,
  `broker.list_pipelines`, `tags.list/get` have HIL evidence pending review; the Modbus paged reads were closed
  in the spec plan on 2026-11-05. Others are "in manifest" only, so every reply must be checked against the
  spec on the real device (like `set_output`, opened ahead of the campaign).
- Sensitive reads: `sms.list`/`sms.get` (phone numbers, content), `config.get` (spec silent on redaction),
  `ota.remote_config_get` (may hold URL/token). Wi-Fi config reads return only `password_set`/`has_password`.
- Gateway command key changed again 2026-11-06 by the user; re-imported into the dev API (key generation 3) and
  verified with signed `system.get_info` and `control.get_status`.

| Approach | Verdict |
|---|---|
| A. Cards read on demand through `runDeviceCommand`; data lives in the browser; every read audited | **Chosen.** Least code; per-viewer data |

## Design notes

- **Cards.** Each card has a "Đọc" button, the time of the read and its age, and per-card errors. It sends its
  commands one at a time (avoids `LANE_FULL`), renders known fields from the spec, and shows unknown or extra
  fields as raw JSON instead of failing. No auto-read on page open (each viewer would send N commands per
  visit).
- **Gating.** The button shows only when the action is available in the verified catalog and the user holds its
  permission; the server enforces both. An offline device shows a clear notice; reads still go out (they
  time out as outcome unknown, which is harmless for reads).
- **Modbus paging.** Follow the spec's page block (`offset`, `limit`, `next_offset`, `total`) up to 5 pages; join
  live values to device names from `get_rtu_devices`.
- **Catalog regeneration.** Pin `18a63e8ed`. New rows default to denied. `sms.send` (B) must not reach the relay
  path: `OutputCommandPolicy` refuses every physical action except `control.set_output/pulse`; add a test. Add
  `sms.send`/`sms.delete` to the high-risk permission set.

## Acceptance

- Catalog regenerated from `18a63e8ed`; exactly the 20 listed actions become available; the 10 new rows other
  than `tags.list/get` and the two Modbus reads stay denied; high-risk set updated.
- Each opened action returns `Executed` on the real gateway with data matching the spec shape; results recorded
  in a table (deviations noted as spec gaps, like `ESP_ERR_INVALID_ARG` for DO pulse).
- The four cards render fixtures built from the spec shapes and the live replies; errors, missing permission,
  offline device and Modbus paging are tested.
- All .NET and frontend tests green; `vue-tsc` clean.

## Risks

- Replies may differ from the spec (fields, units, error codes): defensive rendering + live check per action.
- Non-admin users need roles that include the new permissions (`tag.view`, `mb_rtu.*`, and the existing view
  permissions for ADC/battery/network/time).
- The regenerated catalog changes the catalog hash; clients re-verify it on load (existing behaviour).
- Each read is a signed command on an anonymous lab broker (replay of reads is harmless; noted, not solved).

## Refinement during planning

`modbus.get_rtu_live` items carry only `channelIndex, slaveAddr, cid, value, quality`; tag names, units and
device names live in `modbus.get_rtu_tags` (same permission `mb_rtu.tag_view`). The plan opens it too:
21 actions, not 20. Plan: `plans/261106-1040-monitoring-read-actions/`.

## Decision after red-team (2026-11-06)

The generator rejects spec `18a63e8ed` (§11 states 98 pairs, the table has 104) and the new rows are an
unreleased firmware overlay. User decision: keep the current pin, drop everything Modbus and tags from this round.
Scope is now 15 reads and 3 cards (device & time, network, power & ADC); see the plan.
