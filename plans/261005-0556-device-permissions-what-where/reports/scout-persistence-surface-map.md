## risks
- EF InMemory, used by dev and every test, does not enforce unique indexes or FKs. UNIQUE(UserId, DeviceId) and the role-org FK will look correct in tests even if upsert logic is wrong. The store code and InMemory store must explicitly find-then-update, and the constraints are only provable through model-metadata tests.
- There are no PostgreSQL tests and no Migrate() call. Any raw ON CONFLICT upsert SQL for memberships, and the generated migration itself, will not run in CI (precedent: EfPermissionStore.cs:117-146 and EfAuthorizationEpochStore.cs:42-85 are untested).
- Atomicity: membership upsert, audit row, PolicyVersion Advance and per-device epoch Advance are separate SaveChanges or raw commands today (EfPermissionStore.cs:52-53,117-146; EfAuthorizationEpochStore.cs:38,42-85). A crash between them could leave a revocation applied without the epoch bump (stale SignalR subscription) or the reverse. If a transaction is introduced, check that the raw commands created from GetDbConnection() run inside the EF transaction on Npgsql.
- Existing permission_grants rows with Kind='device-action' (actions view/edit_basics/edit_product/record_measurements/'*'/command names) cannot be mapped automatically to per-org roles, because roles are not seeded. Dropping them silently removes access, and keeping them leaves dead data that MeController/PermissionGrantsController still expose (MeController.cs:26, PermissionGrantsController.cs:39).
- Fixed InMemory DB name 'hms-server-development' (DependencyInjection.cs:142): Identity users likely persist across WebApplicationFactory instances in one test process. New EF-backed membership data would share that state unless InMemory singleton stores are used, as for orgs and devices.
- Name collision risk: Identity already has global 'roles' (AspNetRoles, UsersController /roles, IdentityUserManagement.CreateRoleAsync :57-69) with a unique NormalizedName (snapshot :45-47). Per-org device roles need distinct naming in tables, DTOs and routes to avoid confusion.
- Unique (ParentId, Name) on organizations allows duplicate root names on PostgreSQL (NULL is distinct). Any 'master company' detection by name would be unreliable.
- The two hand-written migrations have no Designer files (20260928120000, 20260928121500). Harmless for apply, but `dotnet ef migrations remove` or rollback tooling relies on neighbouring Designer models. Generate the new migration with the tool, do not hand-write it.

## open_questions
- Should device_memberships use a surrogate Guid Id PK plus a unique (UserId, DeviceId) index (repo convention), or a composite PK (UserId, DeviceId), like device_keysets at ApplicationDbContext.cs:82?
- Enforce 'role.OrganizationId == device.OwnerOrganizationId' in the DB with a composite FK (alternate keys plus a denormalized OrganizationId on memberships), or only in the handler? Owner org and parent are immutable today (EfManagementStores.cs:31,71-76), so an app-level check is viable.
- Should device_memberships.UserId have an FK to AspNetUsers (with Cascade on user delete)? No custom table references AspNetUsers today.
- What happens to existing permission_grants Kind='device-action' rows: migrate to synthetic per-org roles, delete them in the migration, or leave them read-only and unused?
- Membership history: a dedicated device_membership_audits table (shape of license_trust_audits at ApplicationDbContext.cs:163-174) or a generic authorization audit table also covering role edits and role-permission changes?
- Should new columns follow the repo's PascalCase column convention or the snake_case in the approved design (user_id, device_id, role_id)? Only ApplicationUser uses HasColumnName snake_case (ApplicationDbContext.cs:42-43).
- Is a single global 'master company' root required, distinct from other ParentId==null orgs? Currently there is no flag and several roots are allowed (ManagementApiTests.cs:688-692). Is master-admin always org-less (Program.cs:67-73)?
- Must the high-risk permission set (sys.reboot, sys.factory_reset, sys.ota, mqtt.config_edit, eth.edit, net.priority_edit, wifi.sta_edit, wifi.sta_connect) be persisted (e.g. a role IsHighRisk flag or a computed column), or derived in code from the manifest at check time?
