## findings
- Subscribe-time authorization is org scope only; no device-level permission string is checked when joining a device stream. | EV: DeviceEventsHub.cs:76-92 checks existence (81-83), ScopeAuthorization.CanAccessDevice (84-85), revoked (86-87) and epoch (89-91). ScopeAuthorization.cs:72-77 CanAccessDevice == CanAccessOrganization(device.OwnerOrganizationId), built from 'org-scope'/'deny-org-scope' claims plus permissionStore.ResourceGrants (17-31); master-admin = all orgs (34-36). No 'view'/'device.view'/DeviceActionGrants lookup exists anywhere in the hub or delivery path. | IMP: Under the target design, every org member in scope can stream every device. The hub and all three delivery checks must add the device.view membership check (master-admin bypass; in-scope admins with permissions.manage see all).
- The hub tells out-of-scope apart from not-found, which leaks device existence and contradicts the 404 rule. The REST epoch endpoint returns 403 for out of scope. | EV: DeviceEventsHub.cs:82-83 throws DEVICE_NOT_FOUND and 84-85 throws DEVICE_SCOPE_DENIED. DevicesController.cs:68-70 returns Forbid() for out-of-scope or revoked devices on /realtime-authorization, which ManagementApiTests.cs:71-72 asserts as HttpStatusCode.Forbidden for UnrelatedDeviceId. | IMP: Map out-of-scope to DEVICE_NOT_FOUND / 404 and add a separate in-scope-but-no-permission code / 403. ManagementApiTests.cs:71-72 must flip to NotFound.
- The device authorization epoch is advanced in exactly one place: device revoke. No permission grant, scope grant or role change advances it. | EV: Grep for '.Advance(' in src: epochs.Advance only at PermissionContracts.cs:89 (RevokeDeviceHandler.Handle, 84-91), called from DevicesController.cs:144. All other Advance() calls are the global PolicyVersion: PermissionContracts.cs:49,60,72 (grant handlers) and IdentityUserManagement.cs:43 (CreateAsync), 67 (CreateRoleAsync), 85 (AssignRoleAsync). | IMP: Membership upsert/delete must advance the epoch of that device. A role-permission edit or delete must advance the epoch of every device with a membership using that role. Both must also advance PolicyVersion. None of these trigger points exist today.
- Revocation currently evicts through polling reconciliation, not through push from the write path. Reconcile runs every 100ms over every subscription and re-evaluates principal, device state, epoch and scope. | EV: SignalRDeviceEventDeliveryService.cs:21 (PollInterval 100ms), 28-55 loop, 39 ReconcileSubscriptionsAsync, 159-181: refresh principal (169), then device != null && !Revoked && epochs.Current == subscription.AuthorizationEpoch && CanAccessDevice (174-177), else RevokeAndRemoveAsync (179). RevokeAndRemoveAsync sends 'DeviceRevoked' with DeviceRevokedNotification(device, epochs.Current, permissions.PolicyVersion, reason) (218-226), then removes the device backlog (236), the group and the registry entry (252-269). | IMP: An epoch advance on a membership or role change will evict within about 100ms on every replica, because EfAuthorizationEpochStore.Current reads the DB (EfAuthorizationEpochStore.cs:11-15). Advancing the epoch is the cross-replica eviction primitive. Direct registry eviction would reach only the local replica.
- Scope removal is caught by reconcile even without an epoch bump, because CanAccessDevice reads ResourceGrants live. Device-action un-grants are never caught, because realtime never consults DeviceActionGrants. | EV: ScopeAuthorization.cs:26-31 reads permissions.ResourceGrants on each call. SignalRDeviceEventDeliveryService.cs:177 calls it every tick. No DeviceActionGrants call exists in Hubs/*.cs. DeviceActionGrants is used only by DevicePermissionsController.cs:116 and DeviceCommandsController.cs:60. | IMP: Once device.view comes from memberships, either reconcile must read memberships live every tick (DB cost), or membership/role writes must bump the device epoch so the cheap epoch comparison evicts. The epoch bump is needed for immediacy in any case.
- The global PolicyVersion fence makes ANY permission change (even creating an unrelated user) drop queued events silently and evict any connection that has a pending backlog item, labeled AUTHORIZATION_REVOKED. | EV: RealtimeContracts.cs:44-49 requires deviceEvent.PolicyVersion == currentPolicyVersion. SignalRDeviceEventDeliveryService.cs:68-69 drops the event silently at enqueue. 132-134 calls RevokeAndRemoveAsync with the default reason AUTHORIZATION_REVOKED (214) at send time. PolicyVersion is advanced by IdentityUserManagement.cs:43 (user create), 67, 85 and by PermissionContracts.cs:49,60,72. Event PolicyVersion is stamped at publish, DevicesController.cs:123. | IMP: With org-defined roles and frequent membership edits, this causes spurious evictions on unrelated devices. The frontend then marks devices Revoked (DeviceDetailView.vue:268-272) or removes them (App.vue:148-151). The plan should drop or relax the global PolicyVersion clause for eviction and rely on the per-device epoch, or at least not evict on PolicyVersion drift.
- Events are filtered per subscriber only by scope, epoch and revoked state. There is no per-permission or per-event-type filtering and no payload redaction. | EV: Enqueue check SignalRDeviceEventDeliveryService.cs:77-80; send check 127-132; delivery sends the whole AuthorizedDeviceEvent to Clients.Client(connectionId) (140, 249). SignalR groups are maintained (DeviceEventsHub.cs:25,38) but never used for broadcast (no Clients.Group/User/All in src). The only producer is DevicesController.cs:119-126 (eventType 'status', raw telemetry dictionary payload). The backlog coalesces 'status'/'capabilities' (SignalRConnectionBacklog.cs:191-193). | IMP: Delivery must require device.view per subscriber, which the reconcile/enqueue/send checks can share. If future event types (command results, config) need other manifest permissions, a per-event-type permission map is needed at QueueAuthorizedEventAsync (58-90). None exists today.
- Principal refresh failure removes the subscription silently, with no DeviceRevoked notification. | EV: SignalRDeviceEventDeliveryService.cs:198-203 removes the backlog and calls RemoveMembershipFailClosedAsync, which only removes the group and registry (252-269), returning null without SendAsync. Otherwise a re-join between the two steps registers with the new epoch and the stale grants, and nothing bumps the epoch afterwards.

## risks
- Bumping the epoch on a role edit or membership change evicts ALL subscribers of the affected device(s), including users who keep device.view. Without reason-aware auto re-join in both frontend hub copies plus App.vue/DeviceDetailView.vue, legitimate users lose their live stream, and DeviceDetailView labels the device 'Revoked' (DeviceDetailView.vue:268-272).
- The global PolicyVersion clause in RealtimeEventFence (RealtimeContracts.cs:49), enforced at SignalRDeviceEventDeliveryService.cs:68 and 132, will turn every role or membership edit into dropped events and spurious evictions on every device, once PolicyVersion is bumped more often.
- Epoch and PolicyVersion advances commit outside the membership write (EfAuthorizationEpochStore.cs:38, 56-70; EfPermissionStore.cs:52, 128-139). A wrong order leaves a window where a re-join registers with the new epoch and the stale permission, and nothing triggers another eviction.
- DB load: the reconcile loop does a principal refresh plus scope reads per subscription every 100ms (SignalRDeviceEventDeliveryService.cs:21, 167-180). Adding live membership and role-permission reads multiplies this unless cached.
- Multi-replica: the registry and publisher are in-process singletons (Program.cs:31, DependencyInjection.cs:118) with no SignalR backplane (Program.cs:30). Direct registry eviction from a write path reaches only the local replica. Only the DB epoch reaches all replicas, via polling.
- The InMemory development path registers IPermissionStore and IAuthorizationEpochStore as singletons (DependencyInjection.cs:77, 117) and the EF stores as scoped. New membership/role stores must follow the same split, or the hub (transient) and delivery service (scope per tick) will see inconsistent state.
- Duplicate frontend modules (frontend/src/useDeviceOperationsHub.ts vs frontend/src/core/realtime/useDeviceOperationsHub.ts, plus realtimeAuthorization.ts and signalRConnection.ts) can drift if only one copy is updated.
- A silent removal on principal-refresh failure (SignalRDeviceEventDeliveryService.cs:198-203) leaves clients thinking they are still subscribed. Adding a notification changes the assertion at SignalRDeviceEventDeliveryServiceTests.cs:103.

## open_questions
- Should eviction on a role or membership change be coarse (advance the device epoch: all subscribers of the device re-join, works across replicas) or targeted (per-user eviction: needs a cross-replica signal, or reconcile reading memberships live every tick)? The current architecture only supports the coarse epoch approach across replicas.
- Should the global PolicyVersion stay in RealtimeEventFence (RealtimeContracts.cs:49) and the send-time eviction check (SignalRDeviceEventDeliveryService.cs:132), or should the per-device epoch become the only realtime fence?
- Which DeviceRevoked reason codes should the server emit (for example DEVICE_REVOKED, ACCESS_REMOVED, AUTHORIZATION_CHANGED, REALTIME_RESYNC_REQUIRED), and which ones should the client re-join on automatically?
- Should changes to feature permissions (permissions.manage granted or removed) or to resource scope, which change admin 'see all devices in scope' visibility, also bump device epochs? Today scope removal is caught only by the 100ms reconcile through live ResourceGrants reads, and feature changes have no realtime effect.
- For a role edit, should the epoch bump cover only devices whose memberships use the role, found by a device_memberships WHERE role_id query, or every device in the owning org?
- Should future event types beyond 'status' (command results, config) require specific manifest permissions at delivery (a per-event-type map in QueueAuthorizedEventAsync), or is device.view enough for every realtime event in v1?
- Should the duplicate frontend hub modules be consolidated onto core/realtime before the reason-handling change?
