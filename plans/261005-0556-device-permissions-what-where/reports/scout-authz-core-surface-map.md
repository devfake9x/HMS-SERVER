## risks
- InMemoryPermissionStore keeps grants in plain List<> (PermissionContracts.cs:28-30) yet is registered as a singleton (DependencyInjection.cs:77), so concurrent requests can corrupt it in dev/test.
- Advance and the grant insert are separate round-trips with no shared transaction (PermissionContracts.cs:49-51; EfPermissionStore.cs:117-146 runs raw SQL outside EF). New membership writes plus epoch/version advances must be atomic or ordered so a reader never sees the new version with the old state.
- RealtimeEventFence requires event.PolicyVersion == global PolicyVersion (RealtimeContracts.cs:48-49). Advancing the global version on every membership edit drops in-flight events for every device. Consider fencing per device epoch only.
- EfPermissionStore.PolicyVersion runs 2 queries per read (13-24) and is read many times per request and per SignalR loop iteration (SignalRDeviceEventDeliveryService.cs:68, 132, 224). EffectiveOrganizations calls organizations.List() 3 times per call (ScopeAuthorization.cs:33, 36, 37), and OrganizationsController.List calls it once per org (22). Per-device permission resolution must not multiply this.
- Cookie principal roles are stale after role changes (no UpdateSecurityStampAsync in IdentityUserManagement.cs:83-85), which conflicts with immediate revocation for master-admin status on HTTP.
- DevicePermissionsController.cs:181-182 hard-codes a personal email address in source.
- Existing permission_grants rows of Kind 'device-action' (EfPermissionStore.cs:90) need a migration or cleanup decision; leaving them readable keeps the '*' and bare-action paths alive.
- CommandTransportController (CommandTransportController.cs:5-19) has no [Authorize] and returns a static broker/topic description. Outside this area but anonymous.

## open_questions

- Does 'admin in scope' (sees all devices) mean permissions.manage only, or also devices.manage? Several integration tests use devices.manage as the device-listing permission (ManagementApiTests.cs:47, 95).
- What happens to the feature-grant and resource-scope-grant tables? Keep them with latest-wins semantics, or switch to delete-based revocation (no delete API exists today)?
- Where will the canonical (type, action) -> manifest permission mapping and the config.get/config.set data.domain resolver live? Nothing in src carries it; command-catalog.json has only type/action, and the 45 names appear only in docs/architecture-device-mqtt-api-catalog.md.
- Should the commands endpoint switch from always-200 with a code body (DeviceCommandsController.cs:115) to HTTP 404/403 for scope and permission failures, while keeping catalog failures in the body?
- Which canonical name replaces the 'device.command' / 'devices.command' / 'device.commands' trio (PinnedCommandCatalog.cs:40, ManagementApiTests.cs:406, frontend/src/core/auth/permissions.ts:78)?
- Should the master-admin fallback that picks the first organization when the user has none (DeviceCommandsController.cs:48-51) be removed? AuthorizationContext.OrganizationId is never read by Evaluate.
