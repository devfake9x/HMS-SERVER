Covers DevicesController, DevicePermissionsController, DeviceCommandsController and CommandTransportController, the other device-scoped controllers (Provisioning, Licenses, PermissionGrants, Me, DeviceEventsHub), SendDeviceCommandHandler, DeviceAuthorizationPolicy, CommandDefinition, PinnedCommandCatalog, CommandCatalogHash, HmsIdfProvisionalProtocolAdapter, command-catalog.json, the permission store, and where the frontend reads catalogVersion/catalogHash. The only 'Membership' hits are SignalR group helpers (src/Hms.Server.Api/Hubs/SignalRDeviceEventDeliveryService.cs:201,237,252).

## risks
- Enabling catalog rows removes the only production fail-closed fence (DENIED_UNTIL_ACTION_CONTRACT, SendDeviceCommandHandler.cs:74-77). Bug 1 and the '*' wildcard become live unless they are fixed in the same change.
- Changing POST /commands from 200-with-code to 403/404 breaks the frontend's code handling: request() throws 'Request failed (status)' without the body (frontend/src/core/api/adminApi.ts:156), so App.vue:779 and DeviceCommandModal.vue:168-169 lose the CATALOG_STALE and denial codes. ManagementApiTests L424-428 and L447-449 assert HTTP 200.
- Adding properties to CommandCatalogRow changes the catalog hash. Five hard-coded copies must change together (command-catalog.json:3, CommandContracts.cs:165, CatalogTests.cs:13, ManagementApiTests.cs:416, and the plans fixture catalogHash). If they do not, startup throws COMMAND_CATALOG_HASH_MISMATCH (PinnedCommandCatalog.cs:31-33) or clients get CATALOG_STALE.
- CommandDefinition is a positional record with 31 constructor call sites. A non-optional new parameter breaks compilation across 5 test files.
- Existing PermissionGrants rows of Kind 'device-action' hold bare actions and '*'. If any reader keeps using them during the transition, the cross-namespace grants and stale denies persist. Needs an explicit migrate or discard decision.
- Applying the 404 rule only to DevicesController leaves existence oracles open: DeviceCommandsController (200 DEVICE_NOT_FOUND versus other codes), DeviceEventsHub.cs:82-85, PermissionGrantsController.cs:88-91 (403 for a missing device), ProvisioningController and LicensesController.
- Domain-resolved permissions for config.get/config.set need payload inspection before authorization. The payload values are JsonElement after HTTP model binding, and a missing or unknown domain must fail closed.
- A role edit must advance the epoch for every device whose membership uses that role. Missing one leaves SignalR subscribers receiving events (SignalRDeviceEventDeliveryService checks only scope and epoch).
- DevicePermissionsController.Update writes are non-atomic (a Forbid at L84-85 after earlier writes at L87). The replacement must be transactional.
- The frontend has duplicated legacy modules (frontend/src/adminApi.ts and frontend/src/catalogVerification.ts besides frontend/src/core/...). Updating only one leaves stale types.

- What is the config domain to view/edit permission table for config.get and config.set (domains system, network, wifi_sta, wifi_ap, mqtt, adc per docs/architecture-device-mqtt-api-catalog.md:166)? The fixture has requiredPermission null for both.

- For POST /commands, should policy denials become HTTP 403/404 or stay 200 with a code? Which codes replace FEATURE_PERMISSION_REQUIRED and DEVICE_ACTION_PERMISSION_REQUIRED?
- Should a revoked device that is in scope return 403 (current: DevicesController.cs:68-70, 85-87, 105-106), 404, or 410?
- How do device.edit_basics and device.edit_product split UpdateDeviceRequest (Name versus Project/Package/Area)? Do Create and Revoke stay on devices.manage?
- Is POST /devices/{id}/telemetry the device.record_measurements surface? Should it require CSRF and a device permission, given the master-admin integration tests post without CSRF?
- Does a sub-org admin's 'own permissions on that device' come from their own membership role or implicitly from permissions.manage in scope? This decides how the subset check is computed for admins without a membership.
- Should GET /devices/{id}/permissions (or its replacement) require permissions.manage? It currently exposes all user emails to any scoped user.
