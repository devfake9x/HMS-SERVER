# HMS-SERVER management and control plane

## Overview

Build a separate ASP.NET Core 10 backend and Vue 3 frontend for the approved HMS-SERVER management/control plane. The system manages a multi-level master-company hierarchy, nullable device classifications, three-layer authorization, device credentials and keysets, vendor/managed license workflows, broker credential contracts, firmware-compatible command intent, latest status/capabilities, and audited provisioning. The live MQTT/EMQX adapter is deliberately deferred behind a protocol/transport port in this goal because the ESP32 contract may change. It does not ingest telemetry.

This is an implementation goal for HMS-SERVER core control-plane code. HMS-IDF is an immutable external source for previously recorded evidence only in this goal; no further firmware scan or firmware edits are allowed. The server-side importer/bundle workflow is implemented only to the proven contract boundary, with firmware-side importer behavior explicitly deferred.

## Decision baseline

- ASP.NET Core 10 modular monolith with `Api`, `Application`, `Domain`, and `Infrastructure` projects.
- Vue 3 + TypeScript + Vite frontend with feature modules and a typed same-origin API client; generated OpenAPI types remain a future contract-generation layer.
- PostgreSQL + EF Core; latest status and capabilities only.
- A broker/EMQX adapter with dynamic authentication/ACL behind Infrastructure ports; browser never connects directly to MQTT. Live broker integration is a later phase and is not required for the core control-plane implementation.
- SignalR for authorized device status, capabilities, command, license, and provisioning events.
- Direct HMAC with firmware `crypto/cmd_key`; no HKDF/master-secret until firmware changes.
- The provisional protocol profile records the signed JSON command header limit and firmware-proven fields (`type`, `id`, `ts`, nested `data.action`/`data.data`, optional `key_ver`, `ttl_ms`, `dry_run`, `confirm`, `response_topic`, `trace_id`, and final `sig`). Unknown `kid`/`generation` fields are rejected. The application command boundary is implemented independently of live MQTT; exact publish remains `CONTRACT_UNAVAILABLE` until a later server/ACL fixture selects a canonical leaf. A framed command may carry a separate body up to the firmware-proven 131,072-byte whole-message limit only for descriptor rows with `accepts_body=true` (`modbus.check_rtu_config` and `modbus.replace_rtu_config`); the body is not a new command-envelope field.
- Vendor license bytes and server enrollment/keysets are separate aggregates.
- Device capabilities describe availability only; a pinned server command catalog remains the authority for executable actions and permission metadata.
- Production license signing requires an external signer or KMS/HSM boundary; raw private PEM configuration is rejected.
- Release 1 provisions `PRIMARY_ONLY`; unsupported `SECONDARY_ONLY`, `BOTH`, and `FAILOVER` modes are rejected explicitly until fixture-backed support exists.
- Importer bootstrap uses a device-bound one-time challenge/token plus import nonce, expiry, replay protection, bounded body, and local-only authenticated HTTP; human admin passwords never enter bundles.
- Inbound MQTT state is accepted only through a trusted broker-session envelope carrying authenticated publisher identity; missing or inconsistent identity fails closed.
- The server command catalog is generated or pinned from the HMS-IDF descriptor/build manifest with `catalogVersion`/`catalogHash`; unknown hashes deny commands.
- Production secret roots and Data Protection keys are KMS-backed; the license trust store pins `kid` to issuer/public-key/effective interval and audits rotation/revocation.
- SignalR events carry authorization epochs; latest state is coalesced through bounded queues and stale epochs are discarded.

## TDD policy

Every implementation phase follows this order:

1. Write failing contract, unit, or integration tests for the behavior and boundary.
2. Add the smallest seam or infrastructure needed to run the test.
3. Implement/refactor the production code.
4. Add negative and regression cases.
5. Run the phase regression gate before marking the phase complete.

No phase may mark a security or protocol acceptance criterion complete from a UI-only test.

## Problem-first decision record

The real problem is a missing trust boundary between current HMS-IDF behavior and
future server/importer behavior. Three approaches were considered: documentation
only, implementation-first probing, and a pre-cook evidence gate. The third is
selected because it allows deterministic fixtures and source matrices while
preventing invented topics, identity setters, signer behavior or circular
"implementation must pass before cook" gates.

The contract is explicit where source is incomplete. The server must not publish
commands until a server/ACL fixture pins a canonical leaf under the firmware
`/cmd/#` ingress filter; it returns `CONTRACT_UNAVAILABLE` instead of guessing.
For this goal, command use cases are implemented against a recording/deferred
transport. This permits authorization, catalog, idempotency, audit, and
frontend lifecycle work without claiming MQTT delivery. Live EMQX behavior is
owned by the final integration phase and is not a prerequisite for the core
control-plane phases.
Likewise, importer bootstrap,
candidate identity activation and trusted EMQX publisher metadata are
`NEW_FIRMWARE_CONTRACT` items with phase-owned implementation gates.

## Gate states

- `DESIGN_CONTRACT_READY`: plan, evidence, decisions, schemas, fixtures and
  phase gates are internally consistent; no production implementation is implied.
- `IMPLEMENTATION_VERIFIED`: owning cook phases pass their real backend, frontend,
  firmware, EMQX, signer and importer tests.
- `RELEASE_READY`: deployed recovery, load, security, backup/restore, HA and drift
  evidence pass. This goal must stop before the latter two states.

### Current contract re-scout — 2026-09-25

The current HMS-IDF workspace was re-read before this plan update. The
firmware directory contains a `.git` entry, but the available sandbox cannot
resolve it as a Git repository; no commit is claimed. Contract evidence is
therefore pinned to the source paths and SHA-256 file digests recorded in
`plans/reports/260925-hms-idf-contract-rescout.md`, with freshness
`verified: 2026-09-25@workspace-no-git`.

The re-scout confirms the existing command allowlist, direct 32-byte command
HMAC, final `sig` field, 1024-byte exclusive upper bound, required `id`/`ts`,
TTL/future-skew checks, key-version fencing, and the firmware topic/QoS/retain
map. The command-security source fixture additionally pins a volatile
128-entry exact-`id` LRU dedup cache whose expiry sweep requires completed SNTP;
it is not durable, device-scoped or key-generation-scoped. Firmware evaluates
`dry_run` before `confirm` and before post-parse dedup/security verification.
Responses use the `res:` HMAC domain when a command key exists and can be
plaintext when no command key exists. The response-topic validator is syntax
and reserved-segment based but does not prove device-prefix binding, so the
server must bind overrides through ACL and authenticated enrollment metadata.
A deeper MQTT call-path read also proves that the device subscribes to
`<prefix>/<device_id>/cmd/#`, excludes topics ending in `/cmd/res`, and forwards
every other received payload to the command queue; firmware does not select one
canonical command leaf. The active manager disables ESP-MQTT auto-reconnect and
uses a one-second wake debounce with an exponential 2/4/8/16-second path capped
at 30 seconds and 20 attempts per cycle; broker timing, jitter and SUBACK are
not proven. `mqtt_config.c` initializes a 30-second keepalive while the client
constructor falls back to 120 seconds without a protobuf session config, so a
resolved-config fixture is required before choosing an operational value.
Connected wiring ordering is status-topic update, command/response wiring and
subscription, retained capabilities, then status-plane connect. The server
leaf therefore remains a server/ACL contract requiring an end-to-end fixture,
not a guessed `/cmd/execute` path. The active
identity module exposes getters for `enroll/device_info` and vendor identity but
no complete combined importer, and the HTTP license routes prove human
permission middleware rather than a device-bound bootstrap protocol. These facts
remain source evidence; any server/importer behavior beyond them is a
fixture-gated new contract. The publish-path fixture additionally proves that
the firmware generic outbound publisher validates an explicit non-wildcard,
non-retained topic and that command responses are wired to `/cmd/res`; it does
not select a server command leaf. The HTTP/importer trust fixture separately
pins human session authentication and license-route body limits while keeping
device-bound bootstrap, local-only trust, import replay controls and identity
setter behavior as new firmware contracts.

The pre-cook fixture pass extracted 94 `(type, action)` descriptor rows and
computed catalog hash
`dbda8317758e5f25c5a4dee8456841ef3689fea4707cf5a27c30ffad656f78d9`. It also
verified the known topic/session defaults and exercised five license recovery
model cases. A second build-artifact scan pinned build revision
`b774170ff46c393eeb5e495ea37936038d3f4f4f`, object SHA-256
`0543c46dae94186df8c9972abff136f5d1c33f691184548ac3df1eef3c2d6590`, and found
only 89/94 current action strings; the older object is missing
`modbus.check_rtu_config`, `modbus.replace_rtu_config`, `modbus.restart_rtu`,
`system.get_operations`, and `system.set_ntp_servers`. String presence is not
descriptor-pair/order/schema proof, so this is drift evidence and not a
compatible build manifest. The command-contract fixture now joins descriptor
policy (class, permission, confirmation, body, TTL, dry-run, audit, and
deferred-outcome flags) to the 94/94 handler-registration result while leaving
payload/response schema, build condition, side effects, runtime readiness, and
server policy explicitly deferred. These are `CONTRACT_TESTED`/`MODEL_TESTED` artifacts,
not proof of production backend, actual EMQX, or actual NVS importer behavior.

## Historical implementation evidence — 2026-09-29 (superseded)

The core solution now contains the four-project .NET solution, Vue shell,
versioned `/api/v1` controllers, nullable organization/project/package/area
classification model, EF Core management/Identity model, cookie session and
CSRF foundation, three-layer command authorization with explicit deny support,
server catalog metadata/fail-closed checks, provisional command size/time
validation, recording/deferred transport, one-time primary-only provisioning,
license trust/KMS/signer seams, and a bounded SignalR event/authorization-epoch
seam. Device revocation now persists through the EF store and rejects callers
outside their effective organization scope; persisted resource grants,
including explicit descendant denies, participate in management-list
authorization. The current pinned catalog keeps all 94 rows at
`DENIED_UNTIL_ACTION_CONTRACT`; it is not a production command allowlist.

Validation currently passes 72 backend unit tests, 28 backend integration tests,
38 frontend tests, frontend typecheck and frontend production build. PostgreSQL
repositories are selected when `ConnectionStrings:Postgres` is configured;
development falls back to an in-memory provider and must not be treated as
production persistence. Live EMQX/MQTT, firmware importer execution, raw
private-key signing, live SignalR delivery integration, and firmware importer
execution remain open gates. Production registration now fails closed unless
the host supplies both an explicit `ISecretRootPolicy` implementation and an
external non-ephemeral Data Protection provider; these registrations are the
KMS/HSM boundary and still require a real deployment adapter.
API tests verify CSRF filter registration, revoke scope isolation, permission
grant target/resource scope, POST-only bundle download, enum response shape,
catalog/permission no-store responses, and production secret-root/Data
Protection fail-closed startup. Command audits now reserve a unique
device/correlation key, persist a request fingerprint, reject collisions, and
return `IDEMPOTENCY_IN_PROGRESS` for concurrent retries. An unfinished
reservation has a five-minute lease: live reservations remain in progress and
expired reservations return `IDEMPOTENCY_OUTCOME_UNKNOWN` without automatic
reclaim or retry because the transport may already have caused a side effect.
Authorization epochs use a persistent EF store when PostgreSQL is configured,
with an atomic PostgreSQL upsert for multi-replica advancement. The bounded
publisher filters stale epochs, preserves critical lifecycle events instead of
coalescing them, and a hosted SignalR bridge reconciles memberships even when
the event queue is empty before sending to explicit authorized connections.
Provisioning keysets are now encrypted in a persistent `device_keysets` table
with a unique `(device_id, generation)` key; the in-memory generator remains a
development/test seam. License apply now requires an explicit cryptographic
verifier port; the default adapter fails closed until the firmware
license-parser/signature/binding contract is supplied. The frontend command
form consumes the server's 94-row catalog and disables untrusted, stale,
unauthorized, or unresolved actions. License file selection no longer applies
an invented 2,048-byte limit and the DOM file input is cleared after processing.
Permission policy versions use a persistent singleton counter with an atomic
PostgreSQL upsert (`policy_versions`) instead of deriving concurrency-sensitive
versions from `MAX(permission_grants)`.

### Continuation evidence — 2026-09-29

- The command endpoint resolves the actor organization from the persisted
  Identity user scope when the cookie does not carry an `org` claim. A
  conflicting claim is rejected fail-closed; the regression test proves a
  command request cannot depend on a stale or absent claim.
- Identity user creation, role creation and role assignment now advance the
  shared policy version so authorization snapshots cannot remain valid after
  an Identity mutation.
- Device listing now supports a server-side `q` filter while retaining all
  organization, classification and lifecycle predicates.
- SignalR reconciliation removes revoked or stale-epoch memberships without
  requiring a new device event. Group-removal failures cannot retain registry
  authorization, and status/capability coalescing no longer overwrites
  critical lifecycle or command events.
- Command requests must carry the frontend's catalog version/hash. The
  application requires both values, compares them with the trusted server
  catalog, and returns `CATALOG_STALE` before any protocol or transport call
  when either value is missing, blank, partial, or mismatched. The frontend
  revalidates the catalog with a no-store request on focus and immediately
  before submit, then disables the command surface until a trusted matching
  snapshot is available. The backend remains the final authority.
- `EfProvisioningSecretGenerator` persists protected username/password and
  32-byte command-key material by device generation and reloads the winner
  after a unique-insert race. The migration is
  `20260929030014_AddDeviceKeysets`.
- `EfPermissionStore` advances policy versions through the persistent
  `policy_versions` counter and preserves monotonicity when legacy grants
  predate the counter. The migration is
  `20260929032719_AddPolicyVersionCounter`.
- `ILicenseVerifier` is an explicit Application port. The default
  `UnavailableLicenseVerifier` returns `LICENSE_VERIFIER_UNAVAILABLE`; tests
  use a named accepting fixture, so no production path treats raw bytes as a
  verified license.
- Role creation and assignment now require the persisted `users.manage`
  feature permission in addition to the HTTP policy claim. A persisted deny
  therefore overrides a stale or forged allow claim; reserved-role and target
  organization checks remain fail-closed.
- Command authorization now treats a wildcard feature deny as stronger than an
  exact feature allow, with a regression test at the domain boundary.
- SignalR delivery refreshes the Identity principal before reconciliation and
  event authorization. Missing, malformed, deleted, or refresh-failing users
  are removed from the subscription registry and group membership fail-closed;
  refreshed claims replace the stored principal snapshot.
- SignalR hub join and revalidation now refresh the current Identity principal

  claims cannot authorize a new or renewed subscription.
- SignalR `DeviceRevoked` notifications now use an explicit DTO containing the
  device id, current authorization epoch, policy version, and revocation reason
  on both event-delivery denial and periodic reconciliation paths, so clients
  can discard stale revoke events consistently.
- SignalR event `policyVersion` is numeric end to end, matching the persistent
  permission counter and the frontend per-device policy fence. Principal
  refresh now fails closed for locked users and for tickets carrying a stale

- Frontend inventory filters now persist `organizationId`, `projectId`,
  `packageId`, `areaId`, and `q` in the URL and call the server-side device

- The command API now propagates catalog version/hash from the frontend and
  rejects stale metadata with `CATALOG_STALE` before any protocol or transport

### Active security remediation queue - 2026-09-28

Continuation acceptance: command retries must re-check current authorization
before returning cached outcomes; fingerprints canonicalize nested objects but
preserve array order. Expired unfinished claims never trigger transport again.
Realtime delivery must revalidate each subscribed principal against current
resource scope and device epoch, remove denied memberships, and send only to
explicitly authorized connections; group membership alone is not authority.
The frontend must disable submission without a trusted matching action catalog
and must clear selected license files after success or failure. Tests for these
boundaries precede implementation; they do not require any additional firmware
investigation or live MQTT.

The following P0/P1 findings were re-confirmed during the implementation audit
and must be resolved before the core control-plane can be called ready:

- privileged role creation/assignment must be restricted to the master-admin
  boundary and reserved roles must not be delegated;
- permission grants must validate target existence and caller/target
  organization scope;
- wildcard device-action denies must override both exact and wildcard allows;
- command correlation must reserve atomically, persist a request fingerprint,
  reject collisions, and make concurrent retries side-effect free;
- production KMS/Data Protection registration must be backed by a verifiable
  provider boundary rather than a configuration boolean;
- SignalR revocation/reconnect/event-delivery authorization must fail closed
  across the declared deployment topology;
- device command POSTs must enforce CSRF and one-time bundle consumption must
  not be triggerable by an untrusted GET/prefetch.

Each remediation follows the phase TDD gate: a failing regression test, the
smallest application/infrastructure seam, implementation, negative tests, and
phase evidence. These are core hardening tasks and are independent of the
deferred live MQTT/EMQX integration.

## Evidence-gated decisions to freeze in Phase 1
